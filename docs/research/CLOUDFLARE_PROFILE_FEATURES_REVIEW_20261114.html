Estimate how many business profiles fit the monthly platform allowances.

The $5 Workers plan does not cap static business profiles by count. Capacity depends on where profile files and images are stored, their size, account traffic, cache misses, and any dynamic Worker use.

Where these features fit

The target design makes publication work happen when a business changes content. Visitors read published artifacts.

D1 remains the mutable admin authority; KV is fallback lookup cache only. Neither should be touched by an ordinary published profile view.

Feature effect and implementation guard

Five-image horizontal carousel

Business value: show venue, product, team, or work quality before the visitor contacts the business.

  • Each AVIF is 120 KB; all five total 600 KB.
  • First visible/LCP image eager; images 2-5 native lazy.
  • Reserve slide dimensions and test left/right scroll, keyboard, and touch.

FAQ

Business value: answer common objections before a visitor starts a conversation.

  • Static semantic HTML; native details/summary if collapsible.
  • No hydration or Worker request.
  • FAQ rich results are not generally available; Google limits eligibility.

WhatsApp templates

Business value: make the first message easier and clarify intent (booking, order, question).

  • Direct `wa.me` anchor with URL-encoded short text.
  • Normalize international phone format.
  • No Worker redirect, tracking, or API integration.

Current architecture versus additions

Already in target contract

  • D1 mutable records; immutable publication/media in R2.
  • Warm profile static/CDN response, no Worker or database.
  • KV is fallback-only and non-authoritative.
  • Direct public media, hashed names, cache freshness rules.
  • AVIF conditional; WebP compatible default and real-device fallback tests.

Existing product baseline

  • Gallery section/items and managed media exist in the current editor.
  • WhatsApp contact/action exists as a direct link.
  • FAQ section is not in the current section inventory.
  • Cloudflare runtime is not yet deployed; Phase 1 remains incomplete.

Proposed additions

  • Max gallery count and image derivative/byte budgets.
  • FAQ content schema, bounds, semantics, publication tests.
  • Template count, encoding, phone, and privacy rules.
  • Gallery byte-through-LCP and total-scroll budgets.

Phase placement and gates

Current status: dev/staging resources and candidate migrations exist, but there is no complete deployed Worker runtime, no R2 media objects, and Phase 1 acceptance remains blocked. Do not describe this proposal as implemented.

Carousel performance checks

At the current 120 KB/image assumption, loading all slides transfers 600 KB per full gallery view. Load only the actual visible/LCP image eagerly; apply native lazy loading to images 2-5 and verify in target browsers how many are fetched initially and after each left/right scroll. Measure LCP, CLS, first-view image bytes, complete-gallery bytes, CDN hit ratio, R2 reads, and Worker invocations by route. The PRD's 35 KB figure is a cover-image target, not an approved limit for these gallery files.

## Approved Target Choices

- D1 is the canonical mutable store for Core business, page, draft, slug, card, assignment, audit, and publication metadata.
- Application services own authorization, publication sequencing, card transitions, slug workflows, and cross-service coordination. D1 constraints enforce relational integrity and uniqueness; no stored procedures or triggers encode business workflows.
- R2 holds immutable publication output and public content-hashed media. Private originals and draft uploads are not publicly addressable. Each retained publication records its exact object references.
- KV is a non-authoritative cache for slug/version lookups on Worker fallback paths only. It is not authority for slug ownership, access, card state, revocation, or deactivation. A warm static profile hit must not consult KV.
- Admin entry is restricted to NexTap staff with Cloudflare Access on `admin.nextap.services` plus application-level capability authorization on every operation. Public profile delivery, Menu, and admin have separate privileges and bindings.
- Public profile reads do not write D1 or create per-visit application logs. Menu remains a separate product with no runtime Core-to-Menu dependency.
- When `has_menu` is true, the Core profile link contract is `/b/{slug}/menu`. Phase 1 records this contract only; it does not implement the Menu product, Menu page, static publication, or a Core runtime dependency on Menu.

These choices come from the PRD and target sections of [DATA_MODEL.md](../DATA_MODEL.md), with terminology from [CODEBOOK.md](../../CODEBOOK.md). Verified legacy behavior is summarized in the [Phase 1 parity inventory](../research/PHASE_1_LEGACY_PARITY_INVENTORY.md). The owner-approved `/b/{slug}/menu` contract and indefinite, non-reassignable historical-slug aliases in this spec supersede conflicting PRD wording; the PRD remains unchanged. Exact schema, object keys, cache invalidation, route mechanics, and retention values other than historical-slug aliases are not yet approved by this spec.

## Data Ownership and Authorization Contracts

### Canonical state and transaction boundaries

D1 owns mutable Core state: business and page identity/relationships, drafts and ordered sections, canonical slugs and aliases, card lifecycle/current assignment, append-only assignment history, audit/idempotency records, and publication metadata/active pointer. These are logical responsibilities, not an approved table or column schema. R2 owns immutable publication output and content-hashed public media. Publication records identify the exact verified object set. KV may accelerate slug/version lookup only on Worker fallback paths; it cannot authorize or override D1 state, and a warm static Pages profile request does not consult it.

Application services are the only business-workflow boundary. They own validation, authorization, publication sequencing, slug rename/alias reservation, card transitions, idempotency, and coordination with R2/KV/purge. D1 constraints/indexes enforce integrity and uniqueness; no business workflow is placed in SQL procedures or triggers. Keep transactions short and limited to D1-owned atomic changes, such as reserving the old slug while changing the canonical slug, or changing card state with its history/audit record. R2 writes, image processing, cache invalidation, and other external effects are outside the D1 transaction. For cross-service operations, use idempotency and reconciliation; never activate a D1 publication pointer until all referenced immutable output is written and verified. A failed operation reports failure without exposing partial output and leaves the prior valid publication/state intact where the PRD requires it.

Mutable drafts are never served from public storage/cache. A publication is a complete immutable read model associated with a stable page identity and increasing version; rollback selects a retained verified version rather than rebuilding from a draft. Retain five recent profile versions per business for immediate rollback, as required by the PRD. The precise schema, serialization/manifest shape, D1 API/transaction limits, object-key format, and garbage-collection policy remain implementation decisions; this spec does not define them.

### Identity, roles, tenant scope, and service boundary

The human identity boundary is NexTap staff admitted by Cloudflare Access on the dedicated admin hostname and the approved identity provider. An authenticated external subject must map server-side to an approved Core capability/allowlist; admission alone grants no application permission. The existing target model is internal staff administration, not business-owner self-service. Do not derive roles or capabilities from user-editable business/page data, request parameters, slug, or card token.

Every admin service operation checks the authenticated actor's capability and the target business/page scope before reading or mutating data. Treat the stable opaque Core business ID as the tenant boundary and validate page-to-business and branch relationships from canonical records. Deny anonymous, unknown, non-staff, and out-of-scope actors by default, including reads, exports, uploads, publication, card inventory, and destructive actions. Do not accept caller-supplied tenant identity as proof of ownership. Test both allowed staff operations and denied cross-business access; exact capability names and whether staff capabilities are global or further partitioned are unresolved until the legacy outcome/authorization inventory and owner-approved role map are complete.

Only trusted server-side services receive D1/R2/KV credentials or bindings. The browser receives no database credentials, storage write credential, Access secret, signing secret, or service token. Separate admin, public delivery, and Menu privileges/bindings; grant each service only the operations and resources it needs. Public static delivery serves published output and has no mutable-store access. Any future fallback Worker must use only the minimum lookup access needed and must still defer authoritative card, revocation, ownership, and authorization decisions to canonical service logic. Menu receives its stable Core business ID/current slug contract as appropriate, with no runtime Core-to-Menu data/API dependency from profile delivery.

### Migration and compatibility

Current Supabase migrations, application behavior, and tests are evidence for legacy user outcomes and rollback compatibility, not target schema authority. Inventory required outcomes and authorization before designing D1; do not mechanically port RPCs, RLS policies, or legacy table shapes. Target migrations must be reviewed, repeatable/idempotent on disposable D1 targets, preserve stable opaque IDs and required URL/card/publication behavior, and validate uniqueness/references. Cross-system imports are a later phase; they require approved manifests, checksums/counts, focused functional fixtures, and repeatable idempotent execution. Phase 1 uses synthetic data only and makes no production data changes. Backward compatibility of intermediate target schema versions and exact migration-forward/rollback policy remain unresolved until the implementation migration plan is reviewed; no destructive production migration is approved here.

## Data and URL Contracts

### Identity and page records

Preserve stable opaque business and page IDs. A page belongs to a business and may have parent/branch relationships. A normalized slug is a globally unique route address, not identity. Canonical slugs and historical aliases must resolve only to their original page; alias records cannot be reassigned to another business. A rename and alias reservation are one logical D1 operation.

### Drafts and publication versions

Drafts are mutable admin state and are never served from public storage or cache. A publication is a complete, immutable visitor-visible version, associated with a page and monotonically increasing version. The publication projection includes supported page content, enabled sections in saved order, contact projection, language/direction, public media references, and menu availability as ultimately approved.

Publication sequencing must accommodate the D1/R2 transaction boundary: stage a new version and its manifest in R2; verify all output, hashes, and media references; only then activate the corresponding D1 metadata/pointer. Failed or partial publication leaves the prior version active. Reconciliation detects orphaned objects and stale pointers. Rollback selects a retained verified version, never reconstructing from the mutable draft. The PRD retains five recent versions per business for immediate rollback; exact manifest structure and cleanup behavior require approval before implementation.

### Stable URLs, cards, and contact

Preserve `/b/{slug}`, `/c/{token}`, `/b/{slug}/contact.vcf`, and `/c/{token}/contact.vcf`. A token is stable identity for a card and resolves its active assignment; direct-profile QR/NFC links have no token indirection. Every historical direct-profile slug remains an alias to the same page indefinitely and is never expired or reassigned. An old independent QR/NFC destination must continue to open that profile without reprinting. This policy does not change tokenized card routes.

Card state remains canonical mutable state. KV cannot be the sole source for activation, deactivation, reassignment, or revocation decisions. Preserve assignment history append-only. Contract targets are deactivation visible within one minute and reassignment within five minutes, subject to a proven route/freshness mechanism. Contact VCF contains only published fields, valid UTF-8 VCF data, and appropriate attachment/cache headers.

### Menu link contract

The Core-controlled `has_menu` publication field drives a normal profile link to `/b/{slug}/menu` when true. Menu remains a separate product; Phase 1 does not implement its page/product, any static publication behavior, or runtime Core-to-Menu calls. The synthetic `/menu/*` route proof establishes only that the separate route fixture dispatched on the Phase 0 hostname; it does not prove this profile-link behavior. Any implementation belongs to the applicable later product/runtime phase.

## Security, Operations, and Release Controls

### Authorization and secrets

Cloudflare Access admits only approved staff identities to the admin hostname. The application maps the authenticated external subject to an approved capability and authorizes each read/write, including destructive inventory and publication operations. Access is not a substitute for application checks. Deny anonymous, non-staff, and unauthorized capability requests; do not infer roles from user-editable business/profile data.

Store service credentials and signing/identity configuration in environment-scoped Cloudflare secrets or bindings. Keep secrets out of source, client bundles, logs, fixtures, and shared `.env` files; no secret is client-readable. Development and staging credentials are distinct, production credentials are not introduced or used in Phase 1, and rotation/revocation has an owner and tested procedure before a credential is used. Configure staging Access first and verify sign-out, MFA/recovery expectations, admission, and denial before production Access configuration. Record the generated audience only after the staging application is established. The identity provider, MFA/recovery operating procedure, and rotation interval are not fixed by the PRD and require operational approval.

### Backups and restore

The owner-approved RTO is four hours, measured from incident declaration to verified usable service in the recovery environment. The owner-approved RPO is 24 hours. Neither is operationally proven: the prior 183-second local synthetic test is not an RTO measurement, and no representative backup cadence/change-loss rehearsal has demonstrated the RPO. Do not infer either objective from the PRD's separate 30-day legacy rollback target. The dated foundation JSON records an earlier empty export/import state and is not the current migration-status record. The local synthetic restore evidence in the [environment runbook](../../infra/cloudflare/PHASE_1_ENVIRONMENTS.md) is not representative recovery acceptance. Before Phase 1 recovery acceptance, restore non-empty synthetic fixtures into an isolated non-production target and verify migrations/schema, counts, hashes, relationships, R2 object references, and integrity; record explicit start/end boundaries and elapsed time against the four-hour RTO and verify the recovery point against the 24-hour RPO.

### Logging, limits, and monitoring

Record operational request IDs, bounded route/action names, status, duration, environment, and relevant cache/service outcomes. Never log contact values, credentials, auth/session tokens, full card tokens (including URL/query values), draft/publication content, or uploaded bytes. Redact token-bearing paths and query strings before request logging; use stable internal entity references only where needed for audit. Avoid per-visit public profile logs and analytics. Admin audit events are append-only application records with actor, operation, entity reference, bounded metadata, and timestamp; exclude secrets, contact data, content, and full tokens. Define retention and access for operational and audit logs before implementation; exact retention periods remain unresolved.

Rate-limit card resolution, admin sign-in, uploads, and publishing. Public static GET/HEAD delivery should not write D1. Exact thresholds, dimensions, and response behavior require load/abuse assumptions and owner approval; do not invent numbers in configuration. Apply limits at the service boundary before expensive reads/writes or media processing, return a bounded retryable response where appropriate, and ensure a limit or dependency failure cannot change canonical state or publish a partial version. Define alerts/dashboards for D1 busy/errors, failed writes, request failures, cache status, stale versions, failed purge/reconciliation, storage growth, rate-limit events, and restore readiness. On D1/R2/KV or purge failure, fail closed for admin mutations and authorization-sensitive fallback resolution; preserve the prior active publication and expose a bounded error/request ID without leaking internals. Public static content may continue from its already-published artifact while the admin/data path is unavailable.

### Deployment gates

Use separate deployment targets and credentials per environment. Changes to schema and bindings promote development to staging; production binding/configuration execution is deferred to a later authorized cutover phase and requires separate authorization. Require reviewed, repeatable migrations; a clean target build; deterministic contract tests; successful staging integration and authorization tests, including anonymous/non-staff and cross-business denial; isolated restore evidence; secret/log redaction checks; reviewed rate-limit behavior; and explicit owner approval for schema/URL contracts. Deployment checks must verify the target environment/resource identity and reject production mutation from Phase 1 workflows. Define a tested rollback for failed development/staging deployments and migrations; production rollback procedure remains a later cutover approval. Phase 1 must not apply production DNS, data, or configuration changes.

## Acceptance Criteria

Phase 1 is complete only when all of the following have reviewable evidence. Provisioning currently satisfies resource creation and identity inventory only; bindings, cross-environment access testing, schema, migrations, restore, and most operational acceptance remain open:

1. Development and staging have separately identified D1, R2, and KV resources and deployment bindings; tests prove each cannot address the other's mutation targets using normal credentials. Production has a reviewed resource and binding plan, with readiness and rollback criteria; no production resources need to be provisioned or bound in Phase 1.
2. Public/private media access boundaries are documented and tested with anonymous, admin, and cross-environment requests. No draft/original, credential, or private export is readable through a public path.
3. Approved logical schema and application authorization contracts cover stable IDs, businesses/pages/branches, drafts, immutable publication versions, aliases, contact projections, cards/assignments/history, audit, and idempotency needs. D1 contains no business stored procedures/triggers.
4. Access plus application authorization denies anonymous/non-staff and unauthorized actions, and verifies approved capability behavior. Staging sign-out and MFA/recovery expectations are exercised.
5. Migrations are repeatable and idempotent in a disposable D1 target. Constraints reject duplicate canonical/alias slugs and invalid references; application contract tests cover rename plus indefinite alias preservation and card-state/history integrity.
6. A staging backup/export is restored to a separate isolated target and passes integrity checks with recorded counts, hashes, artifact references, and recovery time.
7. Logging and rate-limit configurations have reviewed thresholds and tests proving secret/contact/full-token redaction and enforcement for the protected operation classes.
8. Deployment gates prevent accidental cross-environment binding and prevent production DNS, data, or configuration changes during Phase 1. Production binding/configuration execution is explicitly deferred to a later authorized cutover phase and requires separate authorization.
9. The schema and URL contracts record the owner-approved `/b/{slug}/menu` link when `has_menu` is true, with no Menu implementation in Phase 1, and indefinite resolution/non-reassignment of historical direct-profile slugs. Physical schema approval remains a separate gate.
10. Phase 0 completion and applicable product/alias decisions remain prerequisites for route-dependent implementation. P0.3 route proof is complete under the reviewed standard: the combined Pages static-routing semantics, deployed artifact/hash, route configuration/source, and same-window positive-control Function event with no profile Function event establish no NexTap application-origin request for the observed `/b/{slug}` requests; Cloudflare internal asset storage is excluded from “NexTap application origin.” Preserve warm static Pages delivery with zero Function/Worker, D1/KV/Supabase, or NexTap application-origin access. An individual cache-tier HIT remains unobserved and is not required; do not require `CF-Cache-Status` or `Age` or infer HIT from `CF-Ray`, matching bodies, or absent Function-tail events. This proof does not make Phase 1 ready to execute or authorize public delivery implementation.

Tests should follow [TESTING.md](../TESTING.md): deterministic domain/schema tests, D1/application contract tests, isolated R2 access tests, and Cloudflare-local or staging authorization/restore journeys. Keep fixtures synthetic and mutation targets environment-checked. These are planned Phase 1 checks, not claims that target test infrastructure already exists or has passed.

# Phase 0 Execution Plan: Baseline and Routing Proof

This plan breaks down Phase 0 of the [Cloudflare migration PRD](NEXTAP_LANDING_DELIVERY_AND_SUPABASE_EXIT_PRD.md). The PRD remains authoritative for product behavior and exit criteria. Phase 0 is evidence gathering and disposable routing validation; it does not authorize production DNS, route, data, or configuration changes.

## Goal

Establish a repeatable baseline for current public profile, media, and card journeys, then prove that the target Cloudflare route can serve a warm `/b/{slug}` response as static/CDN content with zero Worker invocations and no database or NexTap application-origin request. The same test hostname must keep `/menu/*` on the separate Menu application.

The current audit is a starting observation, not a Phase 0 pass. P0.2 has a complete desktop/mobile-lab browser matrix for the five owner-supplied profiles. The owner accepted transition to P0.3 with physical-device, synthetic-card, cache-disabled diagnostic, partial-console, and interaction-proxy limitations recorded as unmet/unavailable; none is represented as a measured pass. P0.3's disposable route proof is reviewed under the evidence standard in the P0.4 decision review. Phase 0 remains incomplete.

**Later decision update (2026-11-14):** The owner-approved Phase 1 execution spec resolves the earlier `has_menu` link and historical-slug retention questions: Core links to `/b/{slug}/menu` when enabled, and prior direct-profile slugs remain aliases indefinitely and are never reassigned. This resolves those product-contract conflicts, but does not close Phase 0's remaining evidence gates or authorize route-dependent implementation. Dated notes below preserve the state at the time they were recorded.

## Boundaries

- Use public production pages only for read-only baseline requests. Do not sign in, mutate, publish, purge, or send test traffic that changes customer data on production.
- Run mutable routing, purge, rename, and Menu coexistence cases only on disposable Cloudflare resources and an isolated test hostname.
- Owner-authorized DNS exception for this phase: use only the `phase0` label at Hostinger for the isolated test hostname. Prefer a CNAME to the assigned Cloudflare Pages hostname after Pages accepts the custom-domain association; do not change apex nameservers or existing apex, `www`, `admin`, or `staging` records, and do not change production routes, Worker configuration, or data.
- Use only synthetic profiles and dedicated synthetic card tokens for test cases that require fixture state. Redact card tokens, cookies, authorization headers, contact data, and private media URLs from logs and artifacts.
- Do not treat browser cache as edge cache. Record browser-cache state and Cloudflare response headers independently.
- Preserve raw measurements and screenshots only when they contain public or synthetic data. Keep generated reports under ignored `.e2e/phase-0/` or `artifacts/phase-0/`, not in source control by default.

Do not require a Menu-enabled profile for this baseline because the Menu profile feature is future work and is not present in the current public profile. Stop before the DNS write if Pages rejects the association or certificate issuance. This also avoids the unavailable child-zone path (the zone-create API rejects subdomains; standalone child zones require Enterprise) and avoids purchasing a root domain. Use the separate synthetic Menu Pages deployment only as a `/menu/*` routing fixture; it does not represent the not-yet-implemented Menu profile integration. **Execution:** Pages accepted the hostname, after which Hostinger added only the `phase0` CNAME to `nextap-phase0-proof-20261113.pages.dev`. The custom hostname is active with a valid certificate. The static profile, control Function, R2 media, and proxied synthetic Menu HTML/CSS return 200. R2 cache sequence was `MISS` → `HIT` → purge → `MISS`. Hostinger readback confirms production records are unchanged.
4. The pending Cloudflare production zone cannot prove a Workers Route or R2 custom domain on the parent zone. A Pages custom-domain test can prove custom-hostname static delivery, profile Function bypass, R2 binding access, and path coexistence on one host. Media and Menu Functions will execute; the no-Function gate applies to the profile path. This does not prove direct R2 custom-domain delivery or a Cloudflare Workers Route. A `workers.dev` result alone does not prove custom-hostname behavior.

**Evidence:** environment/hostname note, profile-shape manifest, read-only DNS and route observations, and a list of unresolved owner decisions.

### P0.2 - Current delivery baseline

Run the same tested browser and profile set for cold and warm visits. Keep two browser-cache modes distinct: for the no-browser-cache diagnostic, disable browser cache for each navigation; for the cold/warm pair, start with a fresh context and browser cache enabled, then immediately request the same URL again in that context. Do not bypass or disable the CDN on either path. Record browser-cache mode separately from edge-cache headers so an empty browser cache is never reported as an edge miss. Capture navigation timing, FCP, LCP, TTFB, CLS, request count through LCP, hero-image bytes/duration, response status, console/request failures, language/direction, and horizontal overflow. Measure interaction latency for a harmless supported public action and report it as a lab INP proxy; mark INP unavailable when no representative interaction exists, and do not present the lab proxy as field INP.

- Lab run: use Chrome DevTools Protocol through the available browser tooling (Chrome DevTools AXI for live inspection; the repository's Playwright-based runner for repeatable sampling). Use mobile viewport `390x844`, 4x CPU slowdown, and a documented Slow 3G profile (150 ms RTT, 200 KB/s down, 100 KB/s up) to compare with the existing audit. Keep a desktop control run.
- Preserve a sanitized resource row for every request in each sample: URL path with secrets, tokens, and query values removed; resource type and MIME type; status; transferred and encoded/decoded body sizes when exposed; start time and duration; initiator; and cache headers/status such as `Cache-Control`, `Age`, `CF-Cache-Status`, or `x-vercel-cache` when present. Include CSS, JavaScript, fonts, images, document, and fetch/XHR resources. Summarize request count and bytes by type, and report JavaScript file count/bytes and font count/bytes separately. Do not store cookies, authorization headers, raw card tokens, or private media URLs.
- Repeat each profile and cache mode ten times in isolated browser contexts. Report raw samples, median, p75, tool/browser versions, and the exact network/CPU/cache settings. Do not call this real-device evidence.
- Real mobile run: use a physical low-end Android phone on its local SIM/mobile data, with Wi-Fi disabled. Visit the same profile shapes in Chrome at least five cold and five warm times per selected profile. Capture the device model, Android/Chrome versions, carrier/network type, approximate test location, timestamps, page/media timings, and screenshots or a DevTools trace. Keep the device stationary and note signal changes; do not substitute CDP network emulation for this run.
- Chrome DevTools AXI or an agent browser can automate and inspect a browser session, but neither creates a physical handset or carrier network. Use remote debugging only if the attached Android target is supported by the current CLI; otherwise drive Chrome on the device and capture its DevTools/remote-debugging evidence manually. A throttled desktop run remains useful lab evidence, not the physical-device gate.
- Measure `/c/{token}` only with a dedicated synthetic active card. Confirm status, redirect target, and timing; never print or store the raw token in reports. Measure direct media URLs separately from page-level image requests.

The existing `scripts/observability/observability-baseline.mjs` is not a drop-in Phase 0 runner: it expects `.env.local`, `.env.audit-fixture.json`, authenticated Supabase fixture data, and includes admin journeys. Those legacy-runner files are absent, but their absence does not block the public baseline. The required Cloudflare and Hostinger credentials are already held in the existing ignored `.env.cloudflare.local` and `.env.migration.local` files and were used for the Phase 0 setup. Keep credentials in their service-scoped files; do not consolidate them into a general `.env` or create production-authenticated fixtures for this public test. Run the baseline with Chrome DevTools AXI/Playwright against the selected public URLs and preserve equivalent evidence without secrets.

Report raw rows, median, and p75 for FCP, LCP, TTFB, CLS, transfer bytes, and request counts; label lab interaction latency as a proxy rather than field INP. Report JavaScript and font bytes as observed baseline diagnostics. Do not add a new JavaScript size gate before reviewing the resource and execution evidence; the PRD's existing requirement is that core profile content/actions need no hydration and optional interactions are deferred.

**Evidence:** machine-readable raw sample report with per-request resource rows, concise summary, selected screenshots/trace, and a run manifest containing tool/browser versions, profile URLs, cache modes, and exact network/CPU settings. No secret-bearing HAR or unredacted trace is accepted.

### P0.4 - Review and exit decision

Compare current and Cloudflare lab/device measurements without claiming causation from one metric. Document whether delays are primarily TTFB, image delivery, client payload, or a combination. Record limitations and any route design alternatives if the strict Worker-free gate fails.

The disposable Pages setup fits the current Free-plan proof assumptions; Pages Function requests count against Workers plan quotas. It demonstrates the custom-hostname path for static profile delivery, R2 binding access, and Menu coexistence on one hostname. R2 media and Menu routes invoke Pages Functions; `/b/{slug}` does not. This does not establish direct R2 custom-domain delivery or Workers Route behavior. Resolve whether those are required by the target architecture before Phase 1. Phase 0 is complete only when all of the following are evidenced:

1. Cold/warm measurements cover all five representative profile shapes, media, and a dedicated synthetic card journey.
2. A physical low-end Android/mobile-network run is captured, or its absence is explicitly reported as a blocking unmet gate; emulation does not satisfy it.
3. On the isolated custom hostname, a warm `/b/{slug}` response is Pages static/CDN content with zero Pages Function invocations and no D1, KV, Supabase, or NexTap application-origin request. Evaluate the route using documented Pages static-asset behavior and the artifact/config/source/tail evidence; do not require cache-status/Age headers or claim an observable individual cache HIT.
4. Direct media, purge, slug update behavior, and `/menu/*` coexistence pass on disposable test resources.
5. Evidence is reproducible, sanitized, indexed, and reviewed against the PRD. The only DNS change is an owner-authorized record for the `phase0` label; apex nameservers and existing production records remain unchanged.

The P0.3 Pages route proof is complete under the reviewed evidence standard. Phase 0 remains incomplete while any other required exit gate is unmet, including physical-device and dedicated synthetic-card evidence. If future implementation changes put `/b/{slug}` through a Function, database, or NexTap application service, stop and resolve the route design with the product owner before proceeding.

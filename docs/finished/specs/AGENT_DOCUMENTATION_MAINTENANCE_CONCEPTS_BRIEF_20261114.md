# Agent Documentation Maintenance for the Cloudflare Migration

* **Author:** abdelrahman-elseht
* **Date:** 2026-11-14

## Overview

NexTap's agents need a compact starting point and a dependable way to tell current implementation, approved migration decisions, dated evidence, and future target requirements apart. The repository already has an index, document metadata, phase records, and deterministic link checks; this concept makes their maintenance rules actionable instead of adding a separate documentation framework. The intended users are coding agents and engineers working across the Cloudflare migration while the Next.js/Supabase/Vercel app remains the compatibility baseline.

## Analysis

The main risk is conflicting authority, not a lack of documents. `AGENTS.md` already requires `AGENT_MEMORY.md` to be a replaceable snapshot, calls for documentation health reviews at phase closeout and after substantial reorganization, and says to archive completed work, update inbound links, and record verified issues with regression guards. `docs/README.md` is the navigation hub. `scripts/quality/docs-index.mjs` and `npm run check:docs` validate authoritative-document metadata, index registration, and local links, but cannot verify that prose still matches source, tests, or accepted decisions. Existing session hooks track edit provenance and run focused checks; they are not a semantic documentation review or a recurring phase-status authority.

Keep source ownership explicit. The migration PRD owns broad Cloudflare target requirements and phases 0-6. Phase execution records own phase status, approved exceptions, and dated evidence. Current source, migrations, and tests establish implemented behavior and legacy parity. `CODEBOOK.md` owns stable product vocabulary and invariants. `docs/ARCHITECTURE.md` is a pointer; `docs/legacy/ARCHITECTURE.md` locates the current compatibility implementation. `docs/DATA_MODEL.md`, `docs/TESTING.md`, and `docs/COMPONENTS.md` own their corresponding maps. `docs/README.md` should point to those owners rather than become a second source of detail. Each material claim should make its class clear: verified implementation, compatibility baseline, approved target decision, proposed target, dated evidence, blocked gate, or open question.

The current status boundary must remain exact: Phase 0 and Phase 1 are incomplete; P0.3 route proof is reviewed under its stated evidence standard; phases 2-6 remain PRD target phases, not implemented behavior. Plans and local tests do not establish a phase pass. A review should also preserve supersession links. For example, the owner-approved Phase 1 spec supersedes conflicting PRD clauses for `/b/{slug}/menu` and indefinite historical aliases while leaving the PRD unchanged. Reviewers found stale alias language in `CODEBOOK.md`, `DATA_MODEL.md`, and schema/runbook notes. This is a specific source-to-doc discrepancy to resolve with evidence, not a reason to rewrite the broad PRD silently.

Treat the memory file as a hot snapshot rather than an accumulating log. Keep only a few durable product/architecture invariants, the current verified migration boundary, and high-value navigation pointers. On a phase-status or blocker change, replace obsolete bullets and link to the dated owning record. At session close, remove resolved task facts. The owner set a hard ceiling of 20 nonblank lines and 2 KB; when the snapshot exceeds either limit, replace or remove lower-priority bullets rather than extending it.

Make health review bounded and repeatable. Trigger it at each migration phase closeout and after substantial documentation or source-tree reorganization, as `AGENTS.md` already directs; also include authoritative-document changes that move an ownership boundary or alter a phase decision in the same change review. Review only the affected phase and its linked authoritative docs, implementation, tests, and evidence. Record the review in a dated closeout or reorganization note with: scope and sources checked; confirmed status/authority conflicts; code/test-to-doc discrepancies; archive/consolidation decisions with rationale; broken or changed inbound links; unresolved questions; and checks run. Exit when every finding is corrected or explicitly recorded as an open question with owner/next evidence, status labels agree with phase evidence, and relevant links/index checks pass. Do not run a repository-wide model review in hooks or CI; use deterministic checks for link and metadata integrity and human evidence reconciliation for semantic claims.

The `KNOWN_ISSUES.md` split improves symptom lookup but adds link, ownership, and update-path overhead. Keep `docs/KNOWN_ISSUES.md` as the stable entry point and contribution contract, with category links and a short “when/how to add or update” instruction. Place focused issue records under a dedicated directory by stable domain (for example tooling/hooks, Cloudflare operations, media, and product behavior). Each record retains symptom, verified cause or explicit uncertainty, solution/workaround, regression guard, and links to owning source/docs/tests. Do not duplicate issue text in the index. Preserve old inbound links by updating every reference together and check that new issue paths are registered/linked; category overlap should be handled by one canonical issue with links from other categories. Since the existing file is only 94 lines, the split should be justified by improved lookup and maintained as a navigable index, not treated as a size-reduction success by itself.

### Multi-Lens Review

All seven required EGM reviewers completed: design critic, codebase details, zoom out, comprehension, implementation readiness, structural, and inventive catalyst. The platform's four-agent thread ceiling required concurrent waves, so the reviewers were not all launched simultaneously. No reviewer failed, returned an empty report, or required a retry.

The overlapping findings were: avoid inventing another registry or duplicating ownership; bound reviews by trigger and affected scope; keep memory genuinely replaceable; preserve phase status and supersession evidence; provide one stable issue index and update path; and do not confuse deterministic link checks with semantic drift detection. The distinctive inventive finding is the existing alias/menu authority mismatch described above. Reviewers also noted that Phase 1 telemetry, deployment, authorization, and recovery controls remain partly unproven; documentation must report those limits as evidence gaps rather than deployed capabilities.

## Goals vs. Non-Goals

* **In-Scope Goals:** Keep `AGENT_MEMORY.md` concise and refreshed by replacing stale/resolved facts; define a repeatable phase-scoped documentation/file health review with triggers, inputs, output, and exit criteria; reconcile `CODEBOOK.md`, architecture guidance, data model, and related references against verified implementation and accepted phases 0-6 contracts; preserve explicit target/current/evidence distinctions and supersession links; split issue records into navigable domain files while retaining a stable index and update path; update links and deterministic registration checks when documents move.
* **Out-of-Scope Non-Goals:** Implement Cloudflare migration phases or alter phase gates; declare Phase 0/1 complete or phases 2-6 implemented; rewrite or supersede the migration PRD without an accepted decision; automate semantic truth judgments or archival in CI/hooks; add a second metadata registry, documentation database, or broad doc-generation framework; turn `AGENT_MEMORY.md` into a history; remove legacy architecture or rollback references; change application code or tests as part of this concept brief.

## Alternatives Weighed

* **Keep all existing policy implicit in prose:** rejected because the present documents contain a concrete stale alias/menu discrepancy and the health-review exit conditions are not operationalized. This remains the least-change baseline if the project declines a dated review artifact.
* **Add a new documentation registry or a full-tree automated drift detector:** rejected because the repository already has `docs/README.md`, front-matter ownership/status metadata, and `check:docs`; semantic truth depends on source, phase gates, and evidence that simple phrase matching cannot prove. A new registry would duplicate ownership and create another synchronization burden.
* **Keep every issue in one file indefinitely:** rejected as the final navigation design because agents currently lack a category-level route from a symptom to the owning evidence and regression guard. The counterargument is valid at current size (94 lines): a short index and explicit update path must accompany any split, and file count alone is not a success measure.
* **Copy phase status and target details into memory, CODEBOOK, and architecture prose:** rejected because status changes faster than domain vocabulary and would multiply sources that can go stale. Use short summaries and links to phase-specific owners.

## Key Decisions & Staging for Next Steps

1. Keep existing ownership and deterministic checks; make maintenance triggers and outputs explicit in the current guidance rather than creating a parallel framework.
2. Choose a canonical phase status/evidence location per phase. Keep the index and memory as concise pointers. Preserve the Phase 1 supersession exception and repair stale alias/menu references only against its accepted decision and linked evidence.
3. Apply a claim-level status vocabulary and evidence links when architecture/data/terminology docs are reviewed. Separate verified behavior, legacy compatibility, approved target decisions, proposed target behavior, and unresolved gates.
4. Define the memory ceiling as an editorial guardrail and require replacement on phase, blocker, or task resolution. Avoid duplicating dated evidence or workflow instructions there.
5. Keep phase-closeout and substantial-reorganization reviews as the required triggers. Use a bounded affected-scope checklist, record an outcome, and close only when discrepancies are resolved or explicitly tracked as open questions and relevant index/link checks pass.
6. Split known issues behind the existing `docs/KNOWN_ISSUES.md` entry point. Update all current readers, issue-writing instructions, and any validation that assumes the single-file layout in the same change. Preserve uncertainty labels and the symptom/cause/fix/guard structure.
7. Before implementation, inventory exact references and propose file boundaries; then update the docs index, inbound links, and focused docs tests/checks. Do not move dated evidence out of its owning phase or research record merely to consolidate prose.

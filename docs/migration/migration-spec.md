# Migration specification and phase gates

Every numbered phase below is a future authorization boundary except Phase 0, the documentation audit. All later phases require a separate scoped approval. Approval to write these documents is not approval to implement them. Source evidence and design are in [architecture](../architecture/current-architecture.md), [structure](../architecture/codebase-structure.md), and [plan](migration-plan.md). Current phase evidence is in [status](migration-status.md).

## Gate template

Before each phase, record owner authorization, approved commit, environment/account identity, rollback point and allowed exact operations. Stop if environment guard, backup, previous gate or acceptance evidence is missing. Review complete diff and source/deployment trigger consequences.

Every phase report records: objective and status; authorization/stop gate; scope and non-goals; prerequisites/dependencies; exact files/modules; infrastructure/database changes; ordered tasks; commands/tests and results; measurable acceptance evidence; risks/failure modes; rollback/data implications; downtime; unresolved evidence. Paths below are expected targets, not pre-authorization to edit or deploy them.

## Acceptance evidence for Phase 9 and cutover readiness

Source authority for every phase: **approved Main is the source of truth; Staging will match its code and intended schema.** Phase 2 must compare observed catalogs and migration ledgers against Main and plan forward reconciliation of Staging drift, including `update_business_page`; it does not execute synchronization. Phases 3-9 may validate approved migration candidates derived from Main in isolation. Phase 10 must integrate reviewed work through the approved Main process and prove Staging runs the exact approved release SHA and forward migration set before release acceptance. This direction does not authorize a push, merge, deployment or database change now.

Environment identities, credentials, bindings, hostnames, Auth configuration and sanitized test data remain distinct. Code/schema convergence does not authorize copying Production rows into Staging or promoting Staging data into Production. Record intended and observed schema evidence separately; equal migration counts or an RPC existing in Production alone do not prove alignment.

| Area | Measurable gate |
| --- | --- |
| Performance | zero ordinary Portfolio Supabase requests across all paths; agreed measured targets in migration-plan.md; payload/latency report |
| Security | exactly two initial application deployments with proven route/import/binding separation; Public no credential/write/list; private/cross-business negative tests pass |
| Reliability | deterministic immutable publish, generation CAS, last-good, retries, crash/concurrency recovery and cache bound tested |
| Revocation/privacy | QR/VCF current eligibility/no-store, private contact-photo denial, approved media retention, max page freshness documented |
| Staging isolation | target guard rejects Production; test users/fixtures isolated; copy plan sanitizes and does not emit external effects |
| Recovery | database AND object bytes independently restored from tested backups; owner-approved RPO/RTO/budget |

| Release | Staging matches exact approved Main release SHA and reviewed forward schema migration set; route/provider trigger review, named approver/action scope, Staging acceptance attached |

Targets are not results. A Next build alone is not Cloudflare proof. A code branch is not a hosted environment. Supabase schema changes are reviewed forward migrations; Staging data is never promoted into Production.
